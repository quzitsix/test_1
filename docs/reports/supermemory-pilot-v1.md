## 2. 六轨准确率

| 模型 | blind | memory | oracle | memory−blind | oracle−memory |
|---|---:|---:|---:|---:|---:|
| Qwen3-VL-2B-Instruct | 1/5，20% | 2/5，40% | 1/5，20% | +20 个百分点 | −20 个百分点 |
| Qwen3-VL-8B-Instruct | 3/5，60% | 0/5，0% | 2/5，40% | −60 个百分点 | +40 个百分点 |

每道题保留官方四个选项，其中有一个“无法回答”选项；本子集的五题都被官方标记为可回答。memory 的弃答数：2B 为 1，8B 为 3。这里的弃答指明确选中对应选项，不是解析失败，也不是调用失败；按当前准确率定义计错。

**不能据此声称 2B 优于 8B，或记忆必然降低能力。** 五题全来自 subject 1 的两个录制，前四题来自 session 8，Q204 来自 session 1；跨录制题为 0/5。70 个协议片段是重复观察不同前缀时的计算单位，不是 70 次独立录制，更不是 70 个统计样本。

8B 差值表中的星号来自小样本正态近似。以“3 对由正确变错误、0 对由错误变正确”作简单符号枚举，在假设独立、正负同概率的前提下，双侧尾概率为 `2/2³=0.25`。这个例子说明旧星号不能当可靠显著性证据；本数据还存在同录制题目相关性，正式统计须扩大独立录制/参与者范围。此次保留旧报告，未修改已有评分规则或结果。

8B 的全部 −60 个百分点来自 Q9、Q19、Q204：blind 正确 → memory 弃答。并非三个错误视觉细节替代了正确答案。可以确认的是**答案行为变得更保守**；无法从记录确定原因是未采到、未看清、没写入笔记、笔记有误还是回答时忽略了笔记。

## 4. 抽帧覆盖：预处理 2 fps 不等于模型观看 2 fps

本轮先将允许观察的前缀裁成最长 60 秒的 2 fps 视频，再由 adapter 每片段抽 4 帧。一个完整 60 秒片段的目标时刻是 `7.5、22.5、37.5、52.5` 秒，即约每 15 秒一帧。oracle 的 96 帧上限本轮未触发：每个环境实际报告 36～72 帧，两条视觉轨的采样数量一致。

用冻结计划、代码采样规则与 2 fps 时间网格推算，得到下表。**这是名义时间覆盖分析，不是从服务器视频解码取得的实测帧，也不证明帧内证据可见。**

| 题号 | 原标注证据区间（录制内秒数） | 预计落在区间内的帧 |
|---|---|---|
| Q9 | 248～267 | 262.5；仅 1 帧 |
| Q14 | 120～140 | 127.5；仅 1 帧 |
| Q15，第一个动作 | 294～303 | **0 帧**；相邻采样点为 292.5 和 307.5 |
| Q15，其余动作 | 303～329；343～360；370～404 | 307.5、322.5；352.5；382.5、397.5 |
| Q19 | 210～223；275～288；480～505 | 217.5；277.5；483.5、490、496.5、503 |
| Q204，放电池 | 984～996 | **0 帧**；相邻点为 982.5 和 997.5 |
| Q204，放盒子 | 1025～1033 | 1027.5、1032.5 |

Q15 和 Q204 因而存在明确的**采样风险**。本轮未记录实际 timestamps，下一轮用 trace 验证。即使某区间未直接采到，模型仍可能借助动作后状态推断；即使采到了，也可能因遮挡、模糊或小字而读不出。不能把时间命中率直接当答案可见率。

后续可以统一提高每片段帧数做消融，但提高 oracle 总帧数会增加推理成本；若仍维持 96 帧上限，可能再次均匀删帧。应明确记录实际保留的帧数。不要按 gold 证据为正式测试挑帧，否则改变了黑盒观察条件。

## 5. 为什么首轮花了这么久

以下从归档的 `env_run.ingest_seconds` 与 `latency_ms` 相加，**不包括模型加载、轨道间等待、验证及未计入字段的开销**，不是完整作业墙钟时长。

| 模型／轨道 | 观察阶段合计 | 回答阶段合计 | 两阶段合计 |
|---|---:|---:|---:|
| 2B memory | 57.01 分钟 | 2.99 秒 | 57.06 分钟 |
| 8B memory | 73.64 分钟 | 6.66 秒 | 73.75 分钟 |
| 2B oracle | 10.75 秒 | 51.41 分钟 | 51.59 分钟 |
| 8B oracle | 10.31 秒 | 51.61 分钟 | 51.78 分钟 |

两个 blind 的五题回答分别合计约 1.04 秒和 1.15 秒，模型加载另计。

memory 每个模型生成 70 条笔记。2B 平均每条观察耗时约 48.9 秒，8B 约 63.1 秒；笔记总字节数分别为 284,941 和 191,628，平均每条约 4,071 / 2,738 字节。默认上限为 900 个新 token，但**仅凭字节数不能证明触达 token 上限，更不能断定发生循环复读**。

oracle 的视频采样在 ingest_end 缓存，观察合计约 10 秒，后面的五次回答却合计约 52 分钟。因此它的主要时间落在包含图像预处理、搬运和生成的回答调用内。2B 与 8B 耗时接近，值得检查 CPU 图像预处理和线程开销，但目前不能直接归因；视觉编码、长提示预填充或卸载也需排查。最终只输出一个字母，不代表只做了很少计算。

## 6. 下一步：只对 Q9 做一次诊断

已加入可选 `--trace-file`：记录实际片段采样时间、分辨率、encode/transfer/generate/decode 耗时、输入/输出 token 数、是否触达 token 上限，以及模型生成的笔记正文。默认关闭；记录不被模型读取，不更改问题、选项、提示词或抽帧规则，不要求第三方黑盒模型交出内部记忆。开启时同步当前输入 GPU 以改善计时，因此有额外诊断开销。

`adapter_trace.jsonl` 是 evaluator 的诊断输出，不是官方证据。`generate_seconds` 包括视觉编码、预填充和续写，尚未细分这三者；它不是纯解码速度。`sample` 记录的是 oracle 总上限裁减之前的候选帧，`generate_done.n_images` 是实际输入数量；本轮 Q9 不触发裁减。

服务器上，在上一轮及同一 checkout 的其他实验都结束后执行：

```bash
conda activate meowbench
cd ~/meowbench
git pull --ff-only
python -m pip install -e . --no-deps

nvidia-smi
python scripts/run_real.py \
  --config configs/experiments/supermemory_diagnostic.yaml \
  --tag sm-diag-q9-v1 --dry-run

mkdir -p logs

  --config configs/experiments/supermemory_diagnostic.yaml \
  --tag sm-diag-q9-v1 > logs/sm-diag-q9-v1.log 2>&1 &

```

按首轮 Q9 的阶段计时估算，两轨约 31 分钟，另加加载等开销；这是参考，不是承诺。可以在另一终端先看第一条 note 的诊断，不用等两轨结束：

```bash

```

文件尚未出现说明 adapter 还未完成初始化，先看该目录的 run.log。Ctrl+C 只退出 tail。

```bash
python scripts/summarize_hf_trace.py \
  runs/sm-diag-q9-v1-qwen3-vl-8b-memory/adapter_trace.jsonl
```

汇总只计算已完成调用，重试的所有 PID/尝试都计入；不作为完整作业计时。新 trace 的 `ready` 记录 CPU 线程数、processor 类型及 device_map：

1. 若 encode 占大头，再单独比较 `torch_num_threads: 8`，其余参数不动、使用新 tag。
2. 若生成笔记占大头且多数达到 900-token 上限，再单独比较较短 `note_max_new_tokens`，同时核查细节损失。
3. 若 Q9 的实际帧含有可读证据，但笔记没记录，再研究笔记策略；若笔记已记录而答案弃答，再研究回答阶段。原有问答文本与 gold 不变。
4. 诊断后再做统一提高帧数的消融，并扩展到更多原题与参与者；跨录制评测需要另选确实依赖历史的题。
